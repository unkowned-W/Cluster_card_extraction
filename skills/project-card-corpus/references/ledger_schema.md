# Enriched ledger schema and boundaries

`data/process_csv/project_card_ledger.csv` is a generated UTF-8 CSV with provenance rows for every local card and one `compound_card` row per synthesis-card compound. Counts change as cards change. JSON-array columns are compact JSON strings; parse them as arrays, not comma-delimited text. Empty scalar means missing/unknown, not zero or ambient.

- `compound_key = DOI#compound[index]` is a stable key *for this card ordering*, not a chemical identifier. `compound_index` is zero-based. `local_card_path` and `source_path` locate the original project-relative JSON; no card copies are made. `source_doi`, `card_id`, `ccdc_number`, and `refcode` retain provenance. On compound rows, `ccdc_number` and `refcode` are JSON arrays because a compound may list multiple deposits.
- Composition: `nuclearity` comes from `material_class.nuclearity` (reported total metals, **not necessarily rare-earth count**); `rare_earth_elements`, `other_metal_elements`, `all_metal_elements`, `metal_composition`, `dimensionality`. Missing or inconsistent counts require source verification.
- Synthesis: `reagent_names`, `reagent_formulas`, `ligand_reagent_names`, `solvents` are JSON arrays. The ligand subset requires a reagent role containing the word *ligand*, which is incomplete when source roles are omitted. `synthesis_procedure`, `temperature`, `time`, `ph`, `vessel_or_method`, `workup_and_crystallization`, `yield`, `synthesis_in_main_text`, `si_used` are compound-level card fields, not validated lab protocols.
- Structure: `structural_family` and `structure_description` reflect article extraction; `structure_terms` contains literal English shape keywords found in those fields, not canonical topological labels. Compound rows also list `linked_structure_refcodes`, CCDC numbers, candidate motif statuses and module metal-composition summaries from matched CIF cards. Structure rows carry crystal system, space group, formula moiety, graph availability, CIF-derived topology/shape, `candidate_modules` JSON and `candidate_module_compositions`, `geometry_basis`, and `interpretation_limit`. Algorithmic candidate motifs remain hypotheses, especially with missing atom/bond data or omitted symmetry edges.
- Links: structure rows have `linked_compound_keys` and `match_cardinality`; cardinality >1 means ambiguous exact identifiers. `matched_local_cif_card` means an exact local structure-card match. `no_corresponding_cif` means no exact match and, by project-owner manual review, no corresponding CIF for that compound; `structure_gap_reason` records this basis. This does **not** itself assert that a CCDC database entry is absent. A reported CCDC number alone does not yield CIF-derived structural detail. DOI alone never creates a compound–CIF link. `review_card` rows index scope-aware review claims but are not joined to compounds.
- Property fields (`property_types`, `property_summary`) index reported card content, not full measurement conditions. For comparisons, open `properties.measurements` in the source card.

Recommended retrieval: filter `compound_card` rows by element + reagent/ligand + nuclearity, then narrow by article structural family/shape; follow `linked_structure_refcodes` to structure rows, check `match_cardinality`/graph status, and inspect only selected original cards. For structural analogs, start with same article family and nuclearity, then compare metal composition and shape; shared words or similar nuclearity alone do **not** establish isostructurality.

For unmatched local structures, answer article-level `structure_description`, formula and reported family if present, with a clear source label. State that CIF-derived connectivity, cell/space group or symmetry-complete topology cannot be verified from this corpus. Never infer details from the presence of a CCDC number alone.
